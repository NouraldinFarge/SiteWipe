# Safety case

> **Public-source prerelease candidate undergoing safety, privacy, accessibility, and binary-release validation.**

This is a structured argument for the current candidate's safeguards. It is not a certification, guarantee of complete deletion, or public-release approval.

## Top-level claim

**Claim S0:** The candidate is designed to coordinate destructive browser operations only for a freshly normalized and authorized target, including the explicitly disclosed selected-top-level-site effect of registrable-site page-storage cleanup, preserve explicitly protected data categories, expose uncertainty, and recover extension-owned request shields after interruption.

S0 depends on the claims below and on these assumptions:

- Chrome/Brave enforce their documented extension permission, process-isolation, and API semantics;
- the exact artifact under test matches reviewed source;
- the user either keeps the default detailed review and approves its complete per-run scope/acknowledgements, or intentionally enables the warned direct-cleanup setting and understands that its hidden fresh preflight replaces per-run visibility; and uses a non-compromised browser/device;
- browser APIs may fail, be unavailable, or expose incomplete state, and reports are read with those limits.

## Safety invariants

These are release-blocking invariants, not optional quality goals:

1. A target host matches only itself or a subdomain separated by `.`.
2. A PRIVATE suffix tenant is a registrable boundary; siblings never enter any destructive or verification candidate set.
3. Unknown/public-suffix-only targets cannot authorize destructive work.
4. Exact-origin matching never crosses scheme or effective port; browser-level closed-page storage/cache is skipped when Chrome/Brave cannot preserve that boundary.
5. Cookies are acknowledged as host-scoped even for exact-origin cleanup.
6. Every associated target is normalized, protected-target checked, preflight-bound, displayed separately, and acknowledged when required.
7. Approval precedes job creation, recovery mutation, DNR installation, page injection, tab closing, or data removal.
8. Approval tokens are short-lived, single-use, and context-bound.
9. Detailed review is the default in Standard and Expert modes. `settings_direct` is accepted only when the strict current `skipCleanupReview` setting is `true` after explicit Settings confirmation; the 1.11.63 disclosure migration resets an older saved opt-in to false before admission so the current selected-site and exact-origin warning must be acknowledged; legacy quick/bypass modes remain invalid, and no caller skip flag or raw cleanup route exists.
10. The complete normalized impact and authority snapshot is stored and reconstructed in both modes; altering counts, limitations, requirements, site-access patterns, approved file IDs, or progress-overlay reach/window/control/cap invalidates the approval. Direct mode must truthfully carry false per-run acknowledgements and an empty file phrase.
11. Current effective settings, prepared authorization mode, resolved target/associated scope, browser private-access state, and host-permission inventory must still equal the preflight authority when the token is consumed.
12. Only one live approval may own temporary host access. A durable canonical lease exists before **Clean now** or detailed final approval can arm any normal-window prompt, classifies requested exact access as a disjoint pre-existing/temporary partition, and uses a conservative 30-minute `prompt_pending` recovery window so a late native grant cannot outlive its recovery obligation. Missing access may be requested only from activation two in the exact worker-created, top-frame, packaged-URL, extension-origin, worker-resolved `TAB` context with its raw single-use capability held only in page memory. Admission/removal require the independent exact event and handoff-document-authenticated literal-true/pre-request-absence outcome. Review expiry revokes cleanup authority but cannot prove an already invoked native prompt settled: ordinary maintenance retains its non-runnable tombstone and lease, while only explicit denial/dismissal, both exact grant proofs, or a real browser-session boundary may finish reconciliation. A proven late grant is removed without cleanup and its nonce-bound terminal cancellation is durably replayable. The lease is forgotten only after every temporary pattern is proved absent. A separate preflight-bound inventory records exact, broader, and all-site pre-existing grants, none selected for automatic removal. Private-source cleanup requires exact target access before preflight, so no missing/temporary private pattern enters the durable lease.
13. Every origin/type plan and candidate tab is revalidated against the authorized target and immutable preflight private scope immediately before mutation; progress-overlay tabs are additionally checked against the bound target/current-window/all-tabs scope before each message or injection and again before reinjection after receiver loss.
14. File removal applies only to IDs captured by the preflight as matching and complete and revalidated immediately before deletion for exact live identity, target, completion, and disk presence. Detailed mode also requires the typed target; saved direct mode intentionally skips the phrase without weakening ID or live-record guards.
15. No cleanup code requests `formData`, passwords, bookmarks, passkeys, Sync, or profile-wide time ranges.
16. Verification failure/timeout/absence remains nonzero uncertainty; tab-close timeout is not classified as definite success or failure.
17. SiteWipe-owned DNR state is forgotten only after the owned range is proven empty and any pending install call has settled; no new cleanup may reuse that range while in-memory or durable pending state remains.
18. Completed reports are not persisted whenever private access is enabled or private scope is observed, and persistence applies the preflight-bound privacy settings rather than later settings. Reports truthfully distinguish detailed review from saved direct authorization.
19. A transformed report's checksum covers the transformed content and is never described as a signature.
20. Versioned request/response correlation rejects stale messages; a timeout is an uncertain outcome and cannot silently prepare or authorize a duplicate run.
21. Run-wide duration/query/record ceilings and cooperative cancellation stop scheduling new ordinary work; a missing/replaced active job stops the old run, replacement jobs do not inherit cancellation, and safety finalizers remain allowed to reconcile extension-owned state.
22. Cleanup/review, administration, and install/startup/alarm maintenance acquire a mutually exclusive lifecycle reservation before their first asynchronous admission check. Conflicting actions fail closed, maintenance is coalesced for replay after release, read-only status and active-job cancellation remain available, and stale-job recovery compares identity before writing. Settings import is bounded/schema-checked/allowlisted/confirmed, and Standard/Expert transitions cannot silently revive `webNavigation`.
23. Browser, performance, accessibility, media, synthetic Browser, automated coverage/install/audit/fixture/build, and technical-provenance evidence is invalidated for every version transaction and is never rebound automatically by the artifact builder. The publication gate independently reruns version/source and exact-artifact verification, while pre-bump dependency evidence must match the old lockfile exactly.
24. Cleanup preparation requires an explicit source-window ID and Boolean private state. The popup rejects incomplete window/tab observations, and the worker independently re-reads that exact window before preflight/lease work and after token consumption; absence or mismatch fails closed. A missing-access handoff additionally requires the exact worker-created tab ID, packaged URL, extension origin, top frame, and one worker-resolved `TAB` `contextId`; optional sender `documentId` is never required or a substitute. The raw handoff capability may enter only that document's memory, and direct-open, duplicate, reload, navigation, replacement, wrong-frame/tab/context, replay, or expiry cannot continue authority.
25. Registrable-site browser-level storage cleanup discloses and binds the selected-top-level-site partition effect: target-associated third-party page storage beneath the selected site may be deleted, selected-origin partitions beneath unrelated top-level sites may remain, cookies stay separately host-scoped, and SessionStorage is not used as decisive persistent-partition evidence.

For a fully proved expired grant, the cancellation result is committed after exact reconciliation proves the disposition and before the owned review and lease retire. Pre-commit storage failure retains those non-runnable records; commit-then-reject is accepted only by rereading the identical terminal value. Startup maintenance and authenticated resume therefore converge on the same no-cleanup result.

## Residual risks

- Sites can recreate state after the shield is removed or through mechanisms Chrome does not expose.
- Partitioned-cookie discovery depends on browser-exposed partition metadata and bounded probes.
- Registrable-site browser-level cleanup can delete third-party page storage partitioned beneath the selected top-level site; the same data owner under unrelated top-level sites is outside that run, and selected-origin partitions beneath unrelated top-level sites may remain.
- Exact-origin-only browser-level closed-page storage/cache is deliberately skipped because schemeful-site partition keys do not preserve ports; only exact live-page work runs, so closed-page residue can remain.
- SessionStorage lifetime follows its browsing context and is weaker partition evidence than persistent LocalStorage or IndexedDB.
- Live-page APIs, protected/PWA storage, OPFS, service workers, and private stores vary by browser/version.
- Cancellation occurs between major phases and cannot undo completed deletion.
- The active automated record is authoritative for source-level detailed-review and opt-in-direct contracts, including Settings confirmation, preflight readiness, arm acknowledgement, exact handoff-tab creation/claim, page loss/reload/navigation/replacement, truthful reports, and alternate-route rejection. Fresh exact-artifact installed evidence remains required for native-prompt, lifecycle, incognito, and browser-behavior claims.
- A Chrome API can finish after the extension's timeout.
- Browser permission/content-setting rules, recently closed entries, protocol handlers, identity grants, device grants, favicons, omnibox/top-sites data, and low-level network state may remain.
- A permission granted after activation two can remain temporarily if the handoff page or worker stops before the authenticated outcome and complete admission proof settle; the durable `prompt_pending` lease uses a conservative 30-minute recovery window, survives session loss, and schedules reconciliation on a later wake, but Chrome can refuse or obscure removal and forward exact-artifact installed evidence is still required.
- The permission API does not provide an atomic provenance transaction around a native grant. Exact tab/context/capability binding and independent event/outcome proofs reduce ambiguity but cannot make the transaction atomic. Rollback is limited to preflight-classified temporary origins with complete reviewed/admitted provenance; incomplete or ambiguous outcomes preserve access/recovery state and require user inspection.
- Browser state can change after the final adapter revalidation but before an asynchronous Chrome mutation completes.
- Redacted records can retain identifying metadata or unknown patterns.
- Automated logic tests and ChatGPT in-app Browser synthetic UI checks do not substitute for real installed-extension evidence.

## Release position

The historical P0 implementation remains retired and unapproved. ADR 0011 authorizes the default-off direct mode with current preflight, freshness, permission, file-identity, single-use-route, and truthful-report controls while explicitly accepting the loss of per-run visibility and acknowledgements. Exact installed 1.11.57 remains failed historical evidence; ADR 0013 moves only missing-access activation two from the doomed action popup into the exact worker-created persistent handoff tab, while preserving durable arming, independent grant proofs, permission provenance, exactly-once admission, private-source refusal, and downloaded-file boundaries. Exact installed 1.11.61 is a separate failed historical record under SW-048: ordinary in-session expiry maintenance discarded the invoked prompt tombstone and lease while Chrome's prompt remained open, so a later exact grant produced neither cleanup nor exact reconciliation. Exact installed 1.11.62 is also failed historical evidence under SW-049: Chrome completed cleanup but exposed an undisclosed selected-top-level-site partition effect and an exact-origin port-scope hazard. The corrective source must bind that registrable-site disclosure and skip exact-origin-only browser-level closed-page storage/cache; active automated evidence governs local validation and reproducible-artifact status. Fresh installed Chrome/Brave evidence remains a separate merge/binary-publication gate. The owner has authorized later GitHub and public-release actions, but each remains gated by its own exact evidence and remote policy; authorization cannot substitute for the full installed detailed/direct/incognito/native-prompt/handoff/storage-partition matrix, accessibility run, benchmark, authentic media, exact-head controls, independent review, and stage-specific approval needed for a supported-binary claim. See [ADR 0011](./decisions/0011-optional-direct-cleanup.md), [ADR 0013](./decisions/0013-persistent-permission-handoff-tab.md), the [historical superseded record](./decisions/0004-complete-review-bypass.md), and [release readiness](./release-readiness.md).
