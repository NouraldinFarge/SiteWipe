# Testing strategy and evidence

> **Public-source prerelease candidate undergoing safety, privacy, accessibility, and binary-release validation.**

The exact latest local run date, environment, counts, coverage, and artifact binding live in `docs/evidence/automated-validation-current.json` and its referenced dated record. Installed-extension claims require retained disposable-profile evidence and are not inferred from Node tests or from a normal web page rendered in the ChatGPT in-app Browser. A ChatGPT in-app Browser run may provide separate synthetic UI evidence for layout, semantics, keyboard flow, and review copy, but it cannot exercise `chrome-extension://` privileges, native host-permission prompts, MV3 suspension, incognito routing, or destructive Chrome APIs.

## Local commands

```powershell
npm ci --ignore-scripts
npm run check
npm run test:property
npm run test:coverage
npm run browser:fixture
npm run build:release-candidate
npm run verify:release-candidate
```

`npm run check:publication-gates` is deliberately separate and expected to fail until human and remote evidence exists. It reruns version/source and exact runtime/source artifact verification in-process even when invoked by itself; a failure there is an accurate release status, not a failing unit test.

## Synthetic fixture infrastructure

`tests/browser/fixture-server.mjs` serves only on loopback by default. Its host-aware page can seed bounded localStorage, sessionStorage, IndexedDB, Cache Storage, service-worker cache, Storage Bucket, OPFS, ordinary/partitioned-cookie attempts, and a harmless download where the browser exposes each API. Small, medium, and large page-store scales are deterministic. See `tests/browser/README.md` for disposable-profile host mapping and secure-context limitations.

The fixture server has Node contract tests and loopback HTTP routes that serve the real popup, Options page, and side-panel HTML/CSS/JavaScript, with a surface-specific synthetic browser-API mock injected ahead of each production module. The popup route covers detailed/direct, private/pregranted/transient, permission-denial retry, unsupported-tab, overlay-disabled, and narrow zoom states; the side-panel route covers report tabs, filters, history, runtime errors, verified zero, known residue with unknown totals, incomplete verification, redaction, and bounded-width states; Options covers the production information architecture plus fail-closed initial hydration and recovery with synthetic storage and permission responses. Exact routes and query controls are documented in `tests/browser/README.md`.

A ChatGPT in-app Browser visit to any of those routes must be recorded as **synthetic in-app UI evidence**, not as an installed-extension run. It can support layout, responsive reflow, accessible structure, keyboard/focus flow, and copy review only. Neither fixture infrastructure nor an in-app Browser page loads the runtime ZIP or a `chrome-extension://` origin, changes Chrome/Brave or installed-accessibility status from pending, or supplies native permission-prompt, incognito-spanning, destructive-operation, privileged browser-API, MV3 lifecycle, exact-artifact performance, compatibility, or authentic store-media evidence.

## Integration-test safety rules

1. Create a new browser profile in a test-output directory excluded from Git.
2. Do not sign in or enable Sync.
3. Do not import browser data.
4. Serve fixtures from synthetic local hostnames or loopback ports; never use personal sites.
5. Create only disposable cookies, storage, history entries, records, and files.
6. Record the exact unpacked source tree or ZIP SHA-256.
7. Assert the unrelated control fixture before and after every destructive run.
8. Inspect `chrome.declarativeNetRequest.getSessionRules()` for owned IDs after every terminal path.
9. Delete the disposable profile only after retained redacted evidence has been copied to `docs/evidence/`.
10. Label ChatGPT in-app Browser results as synthetic UI evidence. Never copy them into installed Chrome/Brave, incognito, native-prompt, MV3-lifecycle, or destructive-API result fields.
11. Freeze the exact source tree before an installed run. Do not test from a live unpacked directory while its files are changing. After any source/version change, close every SiteWipe popup and Options page, use the browser's explicit **Reload** control for the unpacked extension, reopen the UI, and verify the manifest version before preparing detailed or direct authority. A popup and service worker loaded from different source states is not exact-version evidence; discard the run and start with a fresh preflight.

## Failure injection

Browser adapters accept injected dependencies in unit tests. Installed-browser failure injection should use test-only fixture controls or controlled extension reload/worker termination; never weaken production guards. A timeout result must state that the underlying operation may still be running.

## Coverage interpretation

The repository enforces minimum overall coverage of **80% statements, 80% lines, 55% branches, and 70% functions**. Exact current percentages belong in the active automated-evidence record rather than this stable policy document. Browser-dependent adapters and the service worker still require installed-browser evidence regardless of aggregate coverage. Low-value percentages do not waive missing installed-browser branches.

Coverage is a navigation aid, not a safety score. Pure shared modules are expected to have high branch coverage. Browser adapters and the service worker require installed-browser coverage/evidence, so a single repository-wide percentage can be misleading. Any threshold should be split by testable layer and must not exclude files merely to inflate the number.

## Evidence retention

Automated CI logs, coverage, integration JSON, screenshots, accessibility results, and package verification should be downloadable workflow artifacts. Only synthetic, redacted evidence belongs in Git. Private profiles, raw reports, downloads, videos with identifiers, and extension IDs must stay outside the repository.
