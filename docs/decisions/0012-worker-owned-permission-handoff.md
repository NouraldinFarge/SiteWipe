# ADR 0012: Make optional-host-permission handoff worker-owned and popup-context-bound

> **Public-source prerelease candidate undergoing safety, privacy, accessibility, and binary-release validation.**

- Status: Superseded only for the same-action-popup activation-two mechanism by [ADR 0013](./0013-persistent-permission-handoff-tab.md); retained as the historical decision and failure record for its durable arm, proof, ownership, and settlement invariants
- Date: 2026-08-21
- Amends: the native-permission continuation in [ADR 0011](./0011-optional-direct-cleanup.md)
- Superseded in part by: [ADR 0013](./0013-persistent-permission-handoff-tab.md)
- Preserves: the deterministic preflight and mutation boundary in [ADR 0003](./0003-destructive-preflight.md)

ADR 0013 changes only the current activation-two surface from the action popup to an exact worker-created extension-owned handoff tab. The historical installed facts and intermediate mechanisms below remain unchanged; they must not be read as the intended 1.11.63 interaction. Exact installed 1.11.61 later exposed a separate settlement defect tracked by SW-048: ordinary in-session review-expiry maintenance discarded an invoked prompt tombstone and lease while Chrome's native prompt was still open. Exact installed 1.11.62 then exposed the separate storage-partition contract defect tracked by SW-049. Neither failure changes this ADR's historical same-popup mechanism or retained ownership invariant.

## Context and installed failure

The exact installed SiteWipe 1.11.38 Standard test used `sitewipe-unreleased-candidate-1.11.38.zip` with SHA-256 `4CE25902BA754F05E33362308B58873BB6F8F437E0BD2ABA4A76F9504D2EC87E` and reached Chrome's native optional-host-permission prompt for the four reviewed patterns:

- `http://example.com/*`
- `https://example.com/*`
- `http://*.example.com/*`
- `https://*.example.com/*`

Chrome accepted that exact request, but opening the native prompt destroyed the action-popup document. The 1.11.38 popup awaited `permissions.request()` and planned to send `runDeepClean` only after the promise settled. Because the popup no longer existed, that continuation never ran. No cleanup job, report, request shield, or fixture mutation occurred, all three fixture snapshots remained unchanged, and the temporary grant was later removed. Incognito and downloaded-file deletion remained off, and no downloaded file was deleted. The fail-closed mutation boundary worked, but the user-approved cleanup did not start.

The installed run also exposed a separate freshness defect. A later popup instance restored the same review after its five-minute expiry and left final approval actionable. The worker correctly rejected the expired token, again without a job, report, shield, or fixture mutation. Worker-side rejection is necessary but does not make stale UI acceptable.

The worker-owned handoff implemented for SiteWipe 1.11.39 closed those source-level continuation and freshness paths, but its exact installed Standard run exposed a second release blocker before the detailed review. Chrome `151.0.7922.172` loaded `sitewipe-unreleased-candidate-1.11.39.zip` with SHA-256 `BAF78DEF05AC5E6960CD5FD98C0FF0CBDDA71688C6F0259C0A0C2A9E5D56A337`. From the seeded `example.com` fixture, **Review cleanup** failed with “The popup document preparing Chrome target access could not be verified. Reopen SiteWipe.” It reached no detailed review, native permission prompt, handoff, temporary-access lease, cleanup job, report, request shield, DNR mutation, or browser-data mutation. Fixture storage was not resnapshotted after the failed attempts, so this record makes no full post-run equivalence claim; incognito and downloaded-file deletion stayed off, and an independent rehash proved the protected downloaded file unchanged.

The 1.11.39 source required `runtime.MessageSender.documentId` during preparation and the Chrome mock supplied that field to every popup message. Chrome's runtime contract makes `MessageSender.documentId` optional, and the installed action-popup sender omitted it. By contrast, `ExtensionContext.contextId` returned by `runtime.getContexts()` is the required context identifier. Treating the optional sender field as mandatory therefore rejected a legitimate popup; merely accepting null or trusting the shared popup URL would remove the intended anti-replay boundary.

Both failures are release blocking. The first affects final continuation whenever browser UI destroys the popup. The second prevents legitimate popup preparation before either authorization mode can run. The earlier one-activation missing-access contract proved incompatible with a durable worker-owned arm and Chrome/Brave's gesture-gated request. The accepted correction therefore makes the second SiteWipe control an intentional authorization boundary: one activation durably arms and confirms only the exact reviewed approval; a second fresh activation invokes the native request and, only after synchronous call acceptance, authenticates that invocation for durable worker continuation.

## Decision

SiteWipe transfers an already prepared missing-access approval to a worker-owned optional-permission handoff during a first SiteWipe activation and awaits the worker's exact durable acknowledgement. That activation arms only and is non-runnable. A second fresh activation in the same still-live popup dispatches capability-authenticated begin without awaiting, synchronously starts `permissions.getAll()` immediately before Chrome's permission request, then dispatches invocation confirm before awaiting anything. Begin and confirm are non-runnable. The popup may send authenticated `confirmCleanupPermissionGrantOutcome` only if the request resolves literal `true` and the pre-request inventory validly proves none of the reviewed temporary origins was already exact- or broad-covered; the durable outcome includes `preRequestTemporaryOriginsAbsent: true`. Independently, one exact complete host-only `permissions.onAdded` event records `promptGrant.complete`. Cleanup and permission removal require both proofs plus `promptInvocation` and matching schema-3 lease ownership provenance. Pregranted admission remains one activation.

For `prepareCleanupReview`, the worker must:

1. require the exact extension popup URL, reject any sender with `sender.tab`, and independently verify the explicit source window ID and private state;
2. perform a bounded `runtime.getContexts()` query and require exactly one exact-URL `contextType: "POPUP"` context with the required opaque `contextId` and browser-correct action-popup metadata; Chrome action popups currently report `tabId: -1` and `windowId: -1`, so the positive source window and its private state remain a separate `chrome.windows.get` proof;
3. bind that context's required `contextId` to the short-lived review while treating `MessageSender.documentId` as optional rather than substituting an empty or caller-provided identity;
4. mint a high-entropy, single-review popup capability, persist only its SHA-256 digest with the review, and return the raw capability only in the response to that popup; and
5. keep the raw capability only in popup memory—never in the persisted review snapshot, session response cache, local storage, report, or debug evidence.

A response retry from the same bound popup context may rotate its capability only before a handoff or pending arm owns settlement. A pregranted review may rebind only after old-context absence; a missing-access review never transfers. Once armed, only the same live popup may perform begin/inventory/request/confirm and report the outcome. Event proof cannot synthesize outcome or pre-request absence. A literal-true outcome with valid absence but no event remains non-runnable after finite resume retries, allowing a delayed event to complete once. Review expiry revokes cleanup authority but does not settle an invoked browser prompt: ordinary in-session expiry, startup, alarm, and maintenance retain its tombstone and lease. Only authenticated exact terminal handoff settlement or a real browser-session boundary may discard the unresolved record; snapshot validation failure creates no cleanup/removal authority and preserves access.

When a normal-window preflight identified missing exact patterns, SiteWipe requires this durable two-activation ordering:

1. the first activation sends `armCleanupApproval` with the raw popup capability and awaits its result;
2. the worker validates the exact prepared review, popup context/capability, lease, expiry, and nonce, persists `armed`, and returns only an exact acknowledgement containing the matching nonce and durable armed status;
3. the first activation ends without invoking `permissions.request()` or submitting cleanup; and
4. a second fresh activation in that same still-live popup dispatches `beginCleanupPermissionPrompt`, synchronously starts `permissions.getAll()` immediately before `permissions.request()` for the preflight-bound missing patterns, and immediately dispatches `confirmCleanupPermissionPromptInvocation`, all without awaiting; and
5. only after the request resolves literal `true` and the pre-request inventory validly proves every reviewed temporary origin absent from exact and broad coverage, that popup sends and awaits `confirmCleanupPermissionGrantOutcome` with `preRequestTemporaryOriginsAbsent: true`. Snapshot throw/rejection/malformed/covered results settle abandoned without outcome and preserve access.

Awaiting the exact worker acknowledgement makes the review durable before native UI can destroy the popup. Activation two preserves the gesture by starting begin and `getAll()`, invoking request, and dispatching invocation confirm without await. Confirm creates non-runnable `promptInvocation`. One exact complete host-only event is required independently. Only the initiating popup may report literal true, and only with valid pre-request absence proof. The event may precede invocation; outcome and event may race afterward. True-only is retained pending a lagging event, not discarded when resume retries end. Permission possession, invocation, event, outcome, or absence proof alone is insufficient.

Before the first activation was enabled, preflight already created a `prompt_pending` permission lease, a worker-generated random handoff nonce, and the context/capability binding. The popup cannot invent any of them. The worker accepts `armCleanupApproval` only from the exact popup URL with no `sender.tab` and after a constant-time comparison of the supplied raw capability with the stored digest. That proof binds the nonce, single-use review token, final detailed/direct approval, normalized target and associated targets, effective settings and mode, source window and private state, browser incognito-access state, complete impact and access inventory, exact file IDs, expiry, and lease. The popup must verify the returned armed status and exact nonce before exposing the second activation. Missing, incorrect, replayed, or superseded capabilities or acknowledgements fail closed. The capability is also required for explicit denied/abandoned settlement and any cancellation asserting `promptNotStarted: true`; another popup cannot settle or cancel the prepared prompt using only its token, nonce, URL, or copied context ID. An extension page other than the action popup, a content script, a web page, or a mismatched/replaced popup context cannot arm or explicitly settle it.

## State and exactly-once admission

The schema-2 handoff has four authority states plus a non-authorizing begin-intent field:

| State                     | May start cleanup?     | Meaning                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `arming`                  | No                     | The worker owns settlement/recovery responsibility while it validates and persists the handoff. An early permission event cannot turn this state into cleanup authority.                                                                                                                                                                                                |
| `armed`                   | No, without all proofs | It represents the exact final approval and context. Admission requires non-runnable intent/`promptInvocation`, exact complete event-backed `promptGrant`, initiating-popup-authenticated literal-true `promptGrantOutcome`, `preRequestTemporaryOriginsAbsent: true`, exact current grant, and authority reconstruction. True-only remains pending for a delayed event. |
| `prompt_intent_tombstone` | No                     | Expiry, invalidation, or reset revoked approval after authenticated begin but within its 30-second confirmation grace. Confirm may convert it to `prompt_tombstone`; authenticated `not_invoked` discards it while preserving access.                                                                                                                                   |
| `admitting`               | No retry               | The single winner crossed a permanent admission boundary. Duplicate popup continuations, permission events, worker wakes, or timeouts cannot retry this nonce as another cleanup.                                                                                                                                                                                       |
| `prompt_tombstone`        | No                     | The approval was invalidated while native browser UI might still settle. It retains only the bounded information needed to recognize and conservatively reconcile that prompt settlement.                                                                                                                                                                               |

The initiating popup may send `resumeArmedCleanup` only after it has durably recorded a resolved-true outcome. `chrome.permissions.onAdded` may also wake the service worker, but event-only wake is insufficient. Neither resume, permission possession, nor event observation may create or repair `promptGrantOutcome`; only `confirmCleanupPermissionGrantOutcome` from the exact bound popup can do so. Conversely, popup outcome cannot manufacture the exact event proof.

Every wake converges through the same serialized lifecycle reservation and fresh checks. Admission requires all of the following:

- an unexpired `armed` handoff with the exact worker nonce, approval token, source context, settings, target, impact, file evidence, matching `prompt_pending` lease, authenticated non-runnable begin intent, and durable context/capability-authenticated `promptInvocation` recorded by immediate confirm after the accepted request call;
- a fresh `permissions.getAll()` inventory that contains every exact pattern classified temporary by that preflight;
- a durable `promptGrant.complete === true` proof built only from one exact host-only `permissions.onAdded` event equal to the complete preflight-classified temporary-origin set after begin;
- a separate durable `{ popupContextId, granted: true, preRequestTemporaryOriginsAbsent: true, recordedAtMs }` outcome recorded only through the capability-authenticated initiating popup after literal true and a valid synchronous pre-request inventory proving no reviewed temporary origin already covered; and
- successful reconstruction and single-use consumption of the ordinary cleanup authorization before any cleanup mutation.

The convergence handles the activation-two race: the exact event may arrive after begin but before invocation confirmation and is timestamp-bounded by `promptIntent`. Outcome and event may persist in either order. If literal true plus pre-request absence is durable but the event lags, bounded resume exhaustion retains the partial `armed`/tombstone record; it does not classify access as external or remove it. A later exact event may complete exactly once. Only after the session record durably contains the full invocation/event/outcome/absence conjunction may the schema-3 permission lease move from proofless to `ownershipProof: reviewed_prompt_grant`. Atomic admission requires that proof and upgrades it to `admitted_cleanup`; any `release_pending` retry retains the same provenance. If review authority expires first, the complete conjunction may no longer admit cleanup: it may only reconcile the exact preflight-classified temporary patterns and durably return a nonce-bound terminal cancellation. Without terminal proof, the invoked tombstone and lease survive ordinary in-session maintenance until a real browser-session boundary.

After that transition, the worker persists a durable job whose identity binds the handoff nonce and a `handoff_admitting` admission phase. For a nonce-bound handoff job, it also persists only the initiating popup `contextId` and capability SHA-256 digest needed to authenticate terminal `resumeArmedCleanup` replay by the surviving initiating popup across worker restart. The raw capability remains only in popup memory and never enters the review record, active job, report, or debug evidence. Only then may the worker remove the consumed session handoff and mark the job admitted. A crash or ambiguous failure at or after `admitting` does not recreate authority or automatically retry deletion; recovery uses the durable job identity, `admitted_cleanup` lease provenance, and ordinary interrupted-job rules.

Exact lease-owned access is re-proved while the armed approval is consumed and twice after durable admission: before any start badge/debug-log presentation, then immediately before the first browser-data adapter. Losing or changing exact access at any checkpoint fails closed before the next observable or mutation-capable boundary.

## Invalidation, expiry, and settlement

A review expiry, authority change, reset, cancellation, malformed state, or mismatch after begin may create non-runnable intent/prompt tombstones; the 30-second confirmation alarm remains separate from five-minute review expiry. Review expiry revokes cleanup authority immediately. Removal requires exact event proof, literal-true authenticated outcome, pre-request absence, and reviewed/admitted lease provenance. A true-only tombstone remains pending for a lagging event; retry exhaustion is not a terminal discard. Ordinary in-session expiry, alarm, startup, and maintenance cannot use current access absence to discard an invoked-prompt tombstone or lease because the browser-controlled prompt may still settle. Exact authenticated terminal handoff settlement may finish reconciliation; otherwise only a real browser-session boundary may retire the unresolved record while preserving incompletely proved access. A complete grant proof arriving after expiry performs no cleanup and reconciles only the exact preflight-classified temporary access before returning a durable terminal cancellation. An intersecting `permissions.onRemoved` event is serialized with review state, changes owned pending/active provenance to `revoked`, and invalidates pending cleanup authority. A later manual regrant cannot reuse the stale event/outcome/session proof. Synchronous throw, invalid/malformed/covered snapshot, and all terminal legacy/orphan/proofless/revoked records create no removable ownership.

The tombstone persists across service-worker suspension, wake, and extension-page closure. It is retired only after exact prompt settlement permits strict reconciliation—including revocation of only the exact patterns classified temporary by that preflight and carrying `reviewed_prompt_grant` provenance—or after a real browser-session boundary establishes that the prior native prompt cannot still settle. A worker restart, extension-page reload, elapsed timer, broad grant, partial event, or failed/unknown permission query is not that boundary. Startup retries release only for schema-3 `reviewed_prompt_grant` or `admitted_cleanup` ownership. Legacy, proofless, and `revoked` records are discarded while access is preserved. Pre-existing and broader user-controlled access is never automatically removed; ambiguous removal preserves a visible recovery obligation.

The popup independently renders review expiry on a live timer, disables stale approval, announces the stale state, and performs a synchronous expiry check before the first activation dispatches the arm and again before the second activation begins its intent/request/confirmation sequence. Those UI checks reduce confusion but do not replace the worker's full fail-closed validation.

## Preserved product boundaries

This handoff applies to both `detailed_review` and `settings_direct` final approvals, including Standard and Expert modes. It does not create a raw cleanup route, a caller-controlled skip flag, a durable reusable approval, or permission-derived intent. Pregranted access remains one SiteWipe final activation. Missing exact normal-window access requires the durable first-arm/exact-ack activation and a second fresh same-document permission activation; detailed mode retains its displayed review, and direct mode retains its saved-setting authorization. Either missing-access path may also include Chrome/Brave's separate browser-controlled confirmation.

Private-source cleanup does not use this missing-access prompt flow. The browser must already have **Allow in incognito** enabled and every exact target pattern pregranted before private preflight can produce authority. The extension cannot enable incognito access and does not persist missing/temporary private target patterns.

The permission handoff does not change downloaded-file policy. Standard mode continues not to delete downloaded files. Expert downloaded-file deletion remains off by default, requires its existing saved setting and preflight-bound completed file IDs, and preserves files and browser records whenever live identity or outcome is uncertain.

## Consequences, source verification, and required evidence

The worker can finish an already durably armed prompt-bound admission after the initiating popup disappears only if that popup first persisted the authenticated resolved-true/absence outcome, the worker also observed the exact complete host-only event, and the complete session proof was committed as `reviewed_prompt_grant` lease provenance. If popup destruction occurs before true-outcome reporting, SiteWipe deliberately preserves the grant and starts no cleanup; event observation or permission possession cannot fill the missing proof. A popup that closes before the second activation cannot transfer its document-bound capability to a replacement. The cost is two SiteWipe activations for missing access, a multi-part proof handoff, schema-3 ownership tracking plus removal invalidation, a small pre-job state machine, a bounded context lookup and capability rotation protocol, a tombstone/reconciliation obligation, more lifecycle serialization, and a permanent no-retry boundary once admission begins.

The superseded 1.11.39 document-ID implementation had an independent adversarial source verdict with no concrete P0/P1 finding: routing 31/31, startup 42/42, focused handoff security 104/104, popup 22/22, and preflight/review/lease 57/57. Its full unit run was 486/487, with the sole expected failure being the pre-bump runtime/stable-input fingerprint mismatch. The installed run then proved that the mocks' unconditional popup `documentId` did not represent Chrome's valid sender shape. Those totals remain historical source facts, but they do not verify the accepted context/capability remediation or close SW-035.

The frozen 1.11.42 remediation had an independent audit verdict of PASS with no concrete P0/P1 finding. Focused checks passed 163/163 (`8+35+14+1+33+42+25+5`), with cleanup-mode/download checks at 10/10. The syntax scan passed across 433 files, and types, ESLint, Prettier, and diff checks passed. One isolated timing case reproduced only under concurrent runner contention, then passed in the 42/42 suite rerun and 10/10 exact-case rerun; the audit classified it as non-product harness contention. The subsequent installed run nevertheless proved that both the worker and mock had assigned the positive source browser-window ID to the action popup, while Chrome reports the popup's own `windowId` as `-1`. That source verdict remains historical evidence, not installed compatibility evidence. The current correction uses a canonical browser-shaped context fixture, worker-side static mutation guards, and a required new artifact/install gate.

The failed exact 1.11.38, 1.11.39, and 1.11.42 runs are historical failure evidence only. The exact current corrective candidate must be loaded into a fresh disposable, unsynced profile and retain machine-readable results for:

- popup preparation when `MessageSender.documentId` is absent; exact unique action-popup context acceptance with Chrome's `tabId`/`windowId` sentinels; independent source-window/private verification including spanning-profile separation; zero/multiple/wrong type/URL/context/sentinel rejection; unavailable/failed `getContexts()` rejection; raw-secret non-persistence; same-context response retry before handoff; pregranted rebind only after old-context absence; and missing-access cross-context conversion into a non-runnable reconciliation obligation rather than authority transfer;
- wrong/missing/replayed capability rejection plus nonce-bound active-job persistence of only context ID and capability digest for an authentic surviving popup's terminal replay across worker restart;
- the exact activation order—first activation sends and awaits `armCleanupApproval`, verifies the matching nonce and durable `armed` acknowledgement, and makes no permission or cleanup call; second fresh activation dispatches authenticated non-runnable `beginCleanupPermissionPrompt` without awaiting, synchronously starts `permissions.getAll()` immediately before `permissions.request()`, immediately dispatches authenticated `confirmCleanupPermissionPromptInvocation` without awaiting either native result, persists `promptInvocation`, and after a literal-true result plus valid pre-request absence sends and awaits authenticated `confirmCleanupPermissionGrantOutcome`;
- detailed and direct Standard/Expert exact grant, denial, dismissal/abandonment, popup destruction, and ordinary popup survival;
- `onAdded` before/after invocation confirmation; exact complete canonical host-only versus partial, unrelated, broad, duplicated, malformed, mixed named-plus-host, named-only, and multi-event inputs; durable event/outcome ordering; popup survival through true-outcome acknowledgement; popup destruction before and after that acknowledgement; broad/pre-existing/manual access; true-only retention and late-event completion; synchronous browser-API throws with authenticated `not_invoked`; popup/event duplicates; denied/abandoned settlement; resume marker non-synthesis; and the joint event-plus-outcome/absence requirement for cleanup and permission removal;
- schema-3 lease transitions from proofless to `reviewed_prompt_grant` only after complete durable handoff proof, then to `admitted_cleanup`; proof retention in `release_pending`; startup retry only for reviewed/admitted ownership; legacy/proofless/revoked access preservation; and serialized intersecting `permissions.onRemoved` invalidation followed by a manual regrant that neither runs cleanup nor becomes removable;
- expiry and settings/target/source/private/reset invalidation while the native prompt is open, the separate 30-second confirmation alarm versus unchanged five-minute review expiry, `prompt_intent_tombstone` conversion to `prompt_tombstone`, late grant settlement, tombstone reconciliation, worker suspension/restart, and real browser-session-boundary handling;
- exactly one nonce-bound durable job/report, temporary exact-access release, no orphan handoff/lease/shield state, and no cleanup on every rejected path;
- target fixture deletion with sibling/lookalike/protected data unchanged, incognito off/on policy, and downloaded files preserved whenever deletion is disabled.

Source and synthetic Browser checks cannot close this installed-native-prompt gate. The focused independent source audit is complete, but until the complete validation/evidence transaction and exact-artifact run of the current corrective candidate pass, publication evidence remains pending.
